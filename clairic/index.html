Clairic on a Phone Line: Two Kinds of System One

Cloudflare released Clairic, a System One extraction model. I put it on the problem my phone lines solve with code combined with a decision model: getting a date, a number or a name out of what a caller said. It lost that fight, and won a different one.

Stack: DialogWright · TypeSafe Jev · Cloudflare Workers AI (Clairic, in preview) · Node

Follows: Jev IVR: A Phone Line You Can Talk To

Measured: October 20, 2026, on 149 labelled utterances, for well under a cent · The design note

Since Jev IVR

Jev IVR was a phone line for a fictional clinic, built to prove one idea: a caller gets a conversation, and you keep a deterministic program you can read, test and diff. The model underneath, TypeSafe's Jev, never generates text. It answers small typed questions about the call, with probabilities, and the code decides. That project has since grown into DialogWright, an open-source framework built from what it taught, and it now runs several lines, including a booking line for a real business and a knowledge-base demo that answers questions from a 123-page benefits booklet. That story deserves its own write-up. This one is about a new model Cloudflare just released.

Two kinds of System One

"System One" is the name for models that answer in one fast pass instead of generating a reply token by token. Until now the System One models I had built on were decision models like Jev (Cloudflare has one of its own, Clef). You give them state and typed questions, and they give back judgments with probabilities. Clairic is the first extraction model of that kind. You give it text, or up to four images, and a set of typed fields, and it gives back values.

A decision model (Jev)An extraction model (Clairic)
You sendThe call's state and typed questions: yes or no, which of these, how muchA text or images, and typed fields: text, number, date, duration, list, estimate
You get backA probability for each answerA value for each field, its position in the text, how sure it is, and how likely the value is not there at all
It neverWrites textWrites text: a text answer is always a span copied from the input

That last row is what made Clairic interesting to me. The rule I built Jev IVR on is that the model selects and never invents, so a wrong answer is always something the caller actually said. An extraction model whose text answers are spans of the input keeps that rule by construction.

How a phone line gets a value today

Getting a value out of speech is most of the work on a phone line, and it is where Jev IVR and then DialogWright spent most of their tuning. The code finds the candidates: every number-like span in what the caller said, every one-to-four-word span that could be a name. Jev answers questions about them: which span is the year, which words are the caller's own name, whether this is a month said as a number. The code builds the value and checks it against the slot's rules: a birth date in the past, an account number of the right length, nothing taken from words said before the question was asked.

An extraction model promises to collapse that into one call. So I measured it.

Round one: what callers dictate

DialogWright's slot types each ship labelled examples: what a caller says, the slot's settings, and the value the slot must produce. I took 118 of them, every date, birth date, account number, name and free-text example that does not depend on an earlier turn, and ran each twice. Once the way a call runs today, the slot asking Jev its own questions and filling from the answers. Once through Clairic, one field of the matching type, the slot's context as its instructions and the example's "today" as Clairic's reference date.

Some of that gap is the test's, not the model's. The slot's rules live in its code, and a one-shot extractor has never heard of them: it cannot know that a parcel's due date is in the past, so "December fifth" is last year's. And the examples were written alongside the slots they test, which is home-field advantage.

The part that is not the test's is dictation:

Caller saideight twenty one eighty four

Should beAugust 21, 1984

Clairic readFebruary 18, 1824

Caller saidFive. Five five two zero four one seven.

Should be55520417

A date said as digits, an account number read one digit at a time, digits in Spanish. That is what a phone line is made of, and it is exactly what the code in front of Jev was built for. Clairic beat the slot on 2 of the 118, and both were a phrase inside a sentence: "blue heron on the lake", and "twelve oak hollow road" out of "yeah my address is twelve oak hollow road".

Those two were the hint.

Round two: what I have no slot for

DialogWright has no slot type for a street address, an amount of money or a code with letters in it. Today an app works around them with a free-text slot that keeps the whole phrase. So I wrote 31 utterances for those values and an email address, each the way a chat user types it and the way a caller says it, and gave Clairic proper instructions for each.

TypedSpoken
A street address4 of 44 of 4
An amount of money3 of 36 of 6
A code with letters4 of 50 of 4
An email address2 of 20 of 3

The amounts are the trick. "Two thousand three hundred forty dollars and fifty cents" came back as 2340.50. "Forty five ninety nine" came back as 45.99. Spoken addresses came back whole: "nine oh five pine street", without the "near the school" the caller added. All of it in 150 to 470 milliseconds.

The spoken codes and emails look like failures and mostly are not. A text answer is a span of the input, so Clairic returned exactly what was said: "f s seven k two q", "m o r g a n at example dot com". Turning that into FS7K2Q is the spoken-to-written step the slot code already takes for digits. Put the two together and five of those seven come right. The other two found the wrong span; the "A" of "A B four four seven one" went missing, most likely read as the word "a".

So the same model that read "eight twenty one eighty four" as 1824 read "forty five ninety nine" as 45.99. Clairic reads numbers in natural phrasing well and dictation poorly. That is not a flaw; it is a description of what it was built for.

Different jobs

Every example Cloudflare shows is a document: an email, a receipt, an invoice, a CSV. Text that was written to be read, where a date is "2026-09-02" and an amount is "$250.00". Speech recognition output is a different animal: numbers spelled out, letters spelled one at a time, a caller correcting themselves mid-sentence. Spoken input is the problem my systems have been tuned on since the first day of Jev IVR, and in this test that tuning shows.

A decision model for what the caller means, code for what they dictated, and an extraction model for what they wrote down.

Where it fits

Two places, both parked until an app needs them.

A slot type for the values that have none. An amount slot and an address slot that take their value from an extraction model, turned on per slot by the app that wants it. Clairic is slower than Jev, so it would run beside Jev's request on the turn, never after it, and the slot's code would still check the value and the read-back would still confirm it, as every slot's does. A code with letters would use Clairic's span and the code's spoken-to-written step.

A photo. This is the one I keep coming back to. Years ago at Apple we built a text service where you sent a photo of your device's serial number and it tried to read it. A caller who texts a picture of a bill, an insurance card or a label is handing over a document, and documents are Clairic's home ground: four images a call, typed fields back, every value with how sure it is. Jev's latest release reads images too, so the next measurement is both models on the same photos.

What's next

Clairic is in preview, priced only on what you send it, and Cloudflare says open weights are coming. The results, the method and both ideas are in DialogWright's design note. When an app needs an amount, an address or a photo, the measurement is ready to run again.

Built for documents, tested on phone calls: it lost on dictation and won on the values I had no answer for.
